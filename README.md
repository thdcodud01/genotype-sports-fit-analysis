# 유전형 기반 운동 적성 추천: 데이터 품질·지표 검증·추천 로직 설계

> 유전자검사 기업 재직 중 참여한 **유전형 기반 운동능력·부상위험 분석 및 종목 추천 서비스** 개발 프로젝트를,
> 공개 가능한 형태로 재구성한 저장소입니다.
> 원본 데이터와 사내 모델 계수는 포함하지 않으며, **구조만 같은 합성 데이터**로 모든 코드가 실행됩니다.
> ([공개용으로 일부 수정됨](#공개용으로-일부-수정된-부분) 참고)

## 1. 문제

서비스는 유전형 → 운동능력·부상위험 점수 → 종목·포지션 추천 순서로 결과를 만듭니다.
프로 선수단 데이터로 모델을 검증하던 중 세 가지 문제가 드러났습니다.

1. **점수를 믿을 수 있는가?** 일부 선수의 점수가 이유 없이 낮게 나왔습니다. 오류 메시지는 없었습니다.
2. **점수가 현장 감각과 맞는가?** 현장 코치가 "이 포지션에 필요하다"고 본 능력과, 데이터가 가리키는 능력의 일치율이 53%에 그쳤습니다.
3. **개인 고객에게도 쓸 수 있는가?** 모델은 선수단(집단) 단위 검증용으로 만들어져, 집단이 없는 개인 고객에게 그대로 적용할 수 있는지 불분명했습니다.

## 2. 가설

| 문제 | 가설 |
|---|---|
| 점수 신뢰도 | 계산 로직이 아니라 **입력 데이터의 표기 방식**이 어긋나 있을 것이다 |
| 낮은 일치율 | 모델이 틀렸다기보다 **비교 기준(측정 방식)이 데이터의 성격과 맞지 않을** 것이다 |
| 개인 적용 | 추천 로직 대부분은 집단 없이도 동작하고, **집단에 의존하는 부분은 일부**일 것이다 |

## 3. 접근과 판단

### ① 데이터 품질부터 확인: 유전형 표기 정규화
- 점수는 `유전형 문자열 → 점수표 조회`로 계산되는데, 같은 이형접합이 `AG`/`GA`처럼 순서만 달라도 **조회에 실패하고 오류 없이 0점** 처리되는 구조였습니다.
- 기준 SNP 리스트를 **유일한 정본**으로 정하고, 점수표와 선수 데이터(147명)를 전수 대조했습니다.
  → **대상 유전자 23종 중 16종**에서 표기 불일치를 확인했습니다.
- 더 위험한 건 겉으로 드러나지 않던 경우였습니다. 점수표와 데이터가 **같은 방향으로 틀려 우연히 맞아떨어지던** 유전자가 많았고, 기준대로 정리된 새 데이터가 들어오는 순간 대량으로 0점이 될 상황이었습니다.
- **판단:** 점수표에 역순 표기를 추가로 등록하는 임시방편 대신, 점수표·데이터를 한 번에 정본 표기로 맞추는 정규화 스크립트를 만들어 데이터가 추가될 때마다 돌리는 파이프라인으로 두었습니다.
- 코드: [`src/normalize_genotype.py`](src/normalize_genotype.py). 기본은 검사만 하고 `--apply`를 주면 반영하며, 다시 실행하면 "변경 대상 없음"이 나옵니다(멱등).

### ② 지표를 올리지 말고, 측정 기준이 맞는지 따지기
**(a) 판정 기준: 엄격 → 완화**
- 코치 요구는 O/X 이진값인데, 데이터 가중치는 0~3점입니다. 기존에는 2점 이상만 "일치"로 봤습니다.
- 코치가 표시한 O는 "관련 있다"는 뜻이므로, 데이터의 1점(약한 연관)도 **같은 방향**으로 보는 게 비교 대상의 성격에 맞다고 판단했습니다. 단, 0점은 불일치로 유지했습니다.
- → 방향 일치율 **53% → 69%** (15개 셀 추가 일치)

**(b) 가중치 산정 기준: 포지션 간 상대비교 → 전체 모집단 기준(z-score)**
- 기존 방식은 포지션 평균끼리만 비교해서, **인원이 적은 포지션의 작은 차이가 크게 부풀려졌습니다.**
  (예: 특정 외야 포지션의 '상황판단력' z = +1.91 → 전체 기준으로 보면 +0.51)
- 전체 선수 분포 대비 "이 포지션이 정말 높은가"를 보는 방식으로 바꾸고, 대표값은 이상치에 강한 **중앙값을 메인, 평균을 검증용**으로 함께 산출했습니다. 점수 구간(0~3점) 컷도 임의의 고정값이 아니라 **분포 기반 백분위**로 정했습니다.
- → 중앙값 기준 **71%**, 평균 기준 **69%** (차이 2%p, 가중치 셀 64% 동일)

> **이 단계에서 가장 중요하게 본 것:** 기준을 바꿀 때마다 숫자가 오르면 "유리하게 맞춘 것 아니냐"는 의심을 받게 됩니다.
> 그래서 **숫자를 목표로 두지 않고**, 방법론적으로 타당한 기준을 먼저 확정한 뒤 나온 결과를 그대로 보고했습니다.
> 전체기준 전환은 일치율을 올리려는 것이 아니라 **포지션 왜곡을 교정하는 것**이었고, 실제로 총 일치율은 69% → 71%로 거의 같았습니다.
> 중앙값과 평균의 결과가 비슷하다는 점은 결과가 계산 방식에 따라 크게 흔들리지 않는다는 근거로 함께 제시했습니다.

- 코드: [`analysis/position_weight_calibration.py`](analysis/position_weight_calibration.py)

### ③ 부상위험을 추천에 얼마나 반영할지: 민감도부터 측정
- 추천 점수 = `적합도 × (1 − λ × 부상위험/100)`. λ가 클수록 부상위험이 큰 종목이 순위에서 밀립니다.
- λ를 바로 정하지 않고, **λ를 0.1~0.5로 바꿨을 때 기존 추천 1순위가 얼마나 바뀌는지**(1순위 변동률, 평균 순위 변동, 기존 1순위의 TOP3 이탈률)를 먼저 측정해 도입 강도를 판단할 근거로 삼았습니다.
- 코드: [`analysis/lambda_sweep.py`](analysis/lambda_sweep.py)

### ④ 개인 고객 적용: 쓸 수 없는 결과는 빼기
- 추천 흐름을 분해해 보니 `유전형 → 고정 점수표 → 능력 점수 → 고정 가중치표 → 종목 적합도`는 **참조 집단 없이도 동작**했습니다.
- 집단이 필요한 건 단 하나, **"선수유형" 라벨**(같은 선수단 평균 대비 상대 판정)이었습니다.
- **판단:** 개인 고객에게는 이 라벨을 **생략**하고 점수 + 종목 추천만 제공하는 안을 택했습니다. 개인을 임의의 집단과 비교해 라벨을 붙이면, 결과가 그럴듯해 보여도 근거가 없기 때문입니다.
- 이에 맞춰 개인 실시간 입력 경로도 설계했습니다.
  - 기존: 선수단 데이터를 미리 적재하고 **이름으로 조회** → 관리자 수동 작업 필요, 실명이 요청에 평문으로 노출
  - 설계안: **접수번호 기반 식별**, 유전자 결손 시 **즉시 422 오류 반환**(조용한 0점 방지), **기존 계산 엔진 재사용**
  - 선수유형 분류 방식(생략 유지 vs 백분위 전환), 인증 방식 등은 팀 검토 과제로 넘겼습니다. 이 저장소에는 설계 판단만 기록했습니다.

### ⑤ 바뀌는 요구에 코드가 아니라 데이터로 대응하기
- 초기 모델은 능력마다 **같은 계산 함수를 하나씩 하드코딩**한 구조(능력 13개 = 함수 13개, 계수도 코드 안에 직접 작성)였습니다.
- 이를 **점수표 CSV + 설정 파일 + 공용 엔진 하나**로 구조화해, 모델·능력·부위가 늘어도 코드는 그대로 두도록 바꿨습니다.
  - 운동능력 지표 8개 → 12개 확장: 점수표 행 추가
  - 부상 부위(아킬레스건) 추가: 점수표 행 추가, **코드 변경 없음**
  - 종목 참조표를 `종목` 1열 → `종목·포지션` 2열 키로 전환 (27종목 → 62블록)
  - 새 모델 추가: 등록부(`registry.py`)에 설정 한 줄 + 참조 폴더 하나
- 코드: [`api/`](api/) (FastAPI)

## 4. 결과

| 항목 | Before | After |
|---|---|---|
| 현장 코치 판단 대비 방향 일치율 | 53% | **69%** (판정 기준 완화) → 전체기준 전환 후 **71%** (중앙값) / 69% (평균) |
| 유전형 표기 불일치 | 대상 23종 중 16종 | **0건** (정규화 파이프라인) |
| 작은 포지션의 가중치 왜곡 | z +1.91 | **+0.51** |
| 운동능력 지표 | 8개 | **12개** |
| 종목 추천 단위 | 27개 종목 | **62개 종목·포지션 블록** |
| 부상 부위·종목 추가 비용 | 코드 수정 | **데이터 파일 행 추가** |

위 수치는 모두 **원본 데이터 기준**입니다. 이 저장소의 합성 데이터로 실행한 결과와는 다릅니다.

## 5. 사업적 의미

- **고객이 받는 결과의 신뢰도:** 표기 오류로 인한 0점은 오류 메시지 없이 리포트에 그대로 실릴 수 있는 문제였습니다. 서비스에 적용되기 전, **데이터 단계에서 걸러내는 장치**를 만들었습니다.
- **지표를 의사결정에 쓸 수 있게 만들기:** 일치율이라는 하나의 숫자를 측정 기준부터 다시 정의하고, 대안 방식(평균)과 나란히 검증해 **"이 숫자를 믿어도 되는 이유"까지 함께 보고**했습니다. 의사결정권자가 숫자 자체보다 근거를 보고 판단할 수 있게 했습니다.
- **B2B → B2C 확장의 걸림돌 정리:** 선수단(기관) 단위로 검증된 모델을 개인 고객에게 확장할 때, 무엇을 그대로 쓰고 무엇을 빼야 하는지 범위를 확정해 **확장 논의를 구체적인 설계로 바꿨습니다.**
- **요구 변경에 강한 구조:** 종목·부위·지표 추가 요청이 들어와도 개발 작업 없이 **데이터 파일 수정만으로 대응할 수 있는 구조**를 만들었습니다.

## 저장소 구조

```
genotype-sports-fit-analysis/
├── README.md
├── requirements.txt
├── data/sample/                       합성 예시 데이터 (샘플 유전형, 기준 SNP 표, 코치 요구표)
├── scripts/make_synthetic_data.py     합성 데이터 생성기 (seed 고정)
├── src/normalize_genotype.py          ① 유전형 표기 검사·정규화
├── analysis/
│   ├── position_weight_calibration.py ② 판정 기준·가중치 기준별 일치율 비교
│   └── lambda_sweep.py                ③ 부상위험 감산 계수 민감도
└── api/                               ⑤ 점수 산출·유형 분류·종목 추천 API (FastAPI)
    ├── main.py
    ├── app/  (core: 엔진·등록부 / services: 산출·추천 / repository: 저장소 / api: 엔드포인트)
    ├── ref/  (점수표·가중치표·설정, 합성값)
    └── scripts/table_to_json.py
```

## 실행 방법

```bash
pip install -r requirements.txt

# ① 표기 문제 확인 (합성 데이터에 원본과 같은 유형의 오류를 일부러 넣어 둠)
python src/normalize_genotype.py            # 검사만
python analysis/position_weight_calibration.py   # ② 일치율 비교 (내부에서 정규화 후 계산)

# ③·⑤ API와 λ 분석
python src/normalize_genotype.py --apply    # 점수표·샘플 표기 반영
cd api && python scripts/table_to_json.py && cd ..
python analysis/lambda_sweep.py
cd api && uvicorn main:app --reload         # http://127.0.0.1:8000/docs
```

합성 데이터를 처음 상태로 되돌리려면 `python scripts/make_synthetic_data.py`를 다시 실행하면 됩니다.

## 공개용으로 일부 수정된 부분

이 저장소는 원본을 그대로 올린 것이 아니라 **공개용으로 재구성**한 것입니다.

| 구분 | 내용 |
|---|---|
| 데이터 | 개인 유전형 데이터는 포함하지 않음. 모든 데이터는 `scripts/make_synthetic_data.py`로 만든 합성값 |
| 모델 계수 | 유전자명(G01~G24), 점수표, 종목 가중치, 코치 요구표, 임계값은 모두 가짜·예시값 |
| 식별자 | 선수·소속 등 원본 식별자를 `sample_id`, `group`, `role`로 일반화. 엔드포인트 `by-name` → `by-id` |
| 재작성 | `normalize_genotype.py`, `position_weight_calibration.py`는 원본 파일이 없어 당시 로직을 바탕으로 다시 작성 |
| 변경 | `lambda_sweep.py`는 원본의 야구 포지션 전용 분석을 전체 종목 대상으로 바꾸고 엑셀 대신 CSV로 출력 |
| 유지 | 공용 점수 엔진(`api/app/core/engine.py`)은 원본 로직 그대로. 나머지 API 코드는 식별자·경로만 바꾸고 로직 유지 |
| 제외 | 개인 고객용 실시간 입력 엔드포인트는 설계 판단만 README에 기록. 초기 하드코딩 모델은 계수가 핵심이라 파일 대신 ⑤에 서술 |
